The idea

Coding agents such as Claude Code and Codex edit audio by running scrubr commands and reading JSON back. People open the same project in a GPU-rendered window built with Rune, hear every edit the agent made, see who made it, and keep or undo each one.

Edits are non-destructive. Source files are never modified. A project is a list of edits applied to the sources, and audio is rendered only when you export. That shared edit list is what lets an agent and a person work on one project.

Why build it

Agent-facing audio tools exist, but each one depends on something else:

  • AudacityMCP exposes 131 tools, but works by driving a running copy of Audacity through its scripting pipe.
  • Audionaut's MCP server needs the Audionaut app installed.
  • Others wrap FFmpeg in a Python server or call a hosted API, such as VocalRemover and MixMake.

On the editor side, Rust terminal editors are small or dormant. Sampitor, the closest match, is about 1,000 lines and was last pushed in January 2023.

No tool ships as one native binary where an agent and a person share an engine, a project file and a history. Agents already work well from a shell, so a careful CLI is enough and scrubr does not need an MCP server.

Goals

In scope

  • An agent can finish a real editing job using only the CLI and the agent guide.
  • A person can open that project, hear each edit, see who made it, and undo or adjust it.
  • Edits are sample-accurate, non-destructive and deterministic.
  • Several tracks in one project, such as a microphone for each speaker and a music bed, mixed down at export.
  • Effects on a selection or a whole track, such as EQ, noise reduction and compression, each one an edit that can be undone.
  • One binary for macOS, Windows and Linux.

Not in v1

  • Recording and MIDI
  • Stem separation: lifting a voice off the music under it. Tried and dropped; the Stem separation section says what was found.
  • A mixer beyond level, pan, mute and solo for each track: no buses, sends or automation
  • Plugin hosting (VST3, LV2, AU)
  • Real-time effect previews
  • Tone and instrument generators, novelty effects such as a vocoder or a wah, and a scripting language for effects
  • A web build. Rune's web target is experimental and WebGPU-only.
  • Any GPL-licensed code, including Audacity's. scrubr is written from scratch.

Who uses it

Agents

Claude Code, Codex, shell scripts and CI jobs. They need commands they can learn from help text, structured output, a stable way to address time, a way to judge audio through numbers and images, and safe retries when the project changes underneath them.

People

Whoever reviews the agent's work, starting with Neil. They need fast navigation through long recordings, playback, a clear history that shows who made each edit, and keyboard-driven editing.

Architecture

The binary is named scrubr. With a subcommand it runs as a CLI and exits. With open, or with no arguments, it opens the GUI. It is built from three crates:

  • scrubr-core: project model, edit log, decoding and encoding, DSP, analysis, peak cache and PNG rendering. No UI dependencies.
  • scrubr-cli: argument and time parsing, JSON and text output.
  • scrubr-gui: the Rune app and cpal playback.

The core never depends on Rune. If Rune stalls, the GUI can move to another toolkit without touching the engine or the CLI.

Project model

A project file holds the sources, the edit log, labels and a head pointer. This example shows the last two edits of an agent session:

{
  "format": 1,
  "version": 7,
  "sample_rate": 48000,
  "channels": 2,
  "sources": [
    { "id": "src1", "path": "raw/ep42.wav", "frames": 172704000,
      "bytes": 1036224044, "mtime": "2026-11-10T09:14:02Z", "hash": "blake3:9f2c…" }
  ],
  "edits": [
    { "id": "e4", "op": "normalize", "lufs": -16.0, "gain_db": 5.4, "author": "codex", "session": "s7" },
    { "id": "e5", "op": "cut", "spans": [["src1", 37932000, 38251200]], "author": "codex", "session": "s7" }
  ],
  "head": "e5",
  "labels": [
    { "span": ["src1", 44935200, 45016800], "text": "check: cough?", "author": "codex" }
  ]
}
  • Edits and labels are stored in source coordinates: a source id and a frame range in that source. Commands still address the timeline. The engine resolves a timeline range to source spans when the edit is made, so ["src1", 37932000, 38251200] is the audio that sat at 12:03.250 to 12:09.900 on the timeline at that moment.
  • Spans point at the source, so an edit keeps its meaning when an earlier edit is undone. Removing one session's edits from the middle of the log does not move later edits or labels.
  • Normalize stores the gain it resolved (gain_db) next to its target, so replaying the log never re-measures the timeline.
  • Each source is stored with its size, modified time and a BLAKE3 hash. Every command compares size and modified time. The full hash is checked when either differs, and always before export. If a source has changed, commands stop with an error instead of editing against different audio.
  • Peak data for drawing lives in a cache folder next to the project and is rebuilt when missing.
  • version increases on every write. Writers use it to detect each other, and agents pass it back with --if-version.

Tracks (M3)

Through M2 a project is one timeline. From M3 it holds one or more tracks: named lanes that share that timeline and are summed for playback and export. A recording made with a microphone for each speaker is one track per microphone. A music bed or a sting is another.

  • One track is the plain case. A project made before M3 opens as a project with one track, and nothing about it changes. The file's format number goes up, and a build that does not know the new format must refuse the file with a clear error, not misread it.
  • Time is shared. cut and keep remove time from every track, so tracks recorded together stay in step. insert adds time to every track, with silence on the others. No command cuts one track alone, so tracks cannot drift apart.
  • Level is per track. gain, fade, mute and normalize take --track, and act on the mix when none is named. Each track also has a level, a pan, a mute and a solo of its own. Pan is one fixed position between left and right, centre unless set, and it does not change over time.
  • Adding a track moves nothing. scrubr track ep42.scrubr add places a file at a position on a new track. That is how a second microphone or a music bed joins a project, where insert splices a file into the timeline.
  • Measuring. analyze, render and transcribe work on the mix, or on one track with --track. A transcript for each track avoids most of the trouble with people talking over each other, when each has their own recording.
  • How it is stored. The main track's audio is the timeline, as before. Every other track's audio is attached to frames of the main track's sources, so a cut, an undo or a revert carries every track with it and none can drift. A stretch of time with no main audio is recorded as silence. The mixer settings are edits in the log, with an author, like the rest.
  • What stays the same. Edits in source coordinates, the batch rule, author and session on every edit, session undo and version checks.

CLI for agents

The CLI follows five rules:

  • Commands name the project file and change it in place. Many small commands are cheap because nothing is rendered until export.
  • Output is JSON when stdout is not a terminal or when --json is passed, and readable text otherwise. Every JSON reply includes ok and project_version.
  • --dry-run on any edit command reports what would change without writing.
  • --if-version N on any edit command refuses the edit, with exit code 3, unless the project is still at version N. Positions an agent worked out from an earlier reply are only valid for that version.
  • Errors say what went wrong and what to run next.

Commands

Batch ruleIn scrubr apply, every range refers to the timeline as it was before the batch. The engine resolves them all against that one timeline. An agent can cut all 38 silences found by one analyze call in one step, without recomputing positions after each cut.

JoinsCuts, keeps and inserts crossfade across each join, 5 ms by default, because an agent can't hear a click. --crossfade 0 gives a hard, sample-exact join.

Example session

You imported the episode and trimmed both ends. The agent takes it from there:

$ export SCRUBR_AUTHOR=codex SCRUBR_SESSION=s7
$ scrubr analyze ep42.scrubr --loudness --silence -45dB:1s > report.json
# agent turns report.silence into cuts.json
$ scrubr apply ep42.scrubr --ops cuts.json --if-version 2
$ scrubr normalize ep42.scrubr --lufs -16
$ scrubr cut ep42.scrubr 12:03.25..12:09.9
$ scrubr label ep42.scrubr add 14:18.5..14:20.2 "check: cough?"
$ scrubr render ep42.scrubr --png check.png
$ scrubr export ep42.scrubr out/ep42.flac

The analyze call returns:

{
  "ok": true,
  "project_version": 2,
  "timeline_seconds": 3449.0,
  "loudness": { "integrated_lufs": -21.4, "true_peak_dbtp": -7.2, "range_lu": 8.1 },
  "silence": [
    { "start": 3.20, "end": 4.85 },
    { "start": 412.10, "end": 414.02 }

The agent passes that project_version back as --if-version 2. If you edited the project after the analysis, the cuts are refused instead of landing in the wrong places.

Agent guide

scrubr help --agent prints a one-page guide: the workflow, time addressing, the batch rule, version checks, exit codes and a worked example. The repo ships the same text as AGENTS.md, so Codex and Claude Code pick it up when working in a project folder.

GUI for people

  • Stereo waveform drawn from the peak cache under an overview of the whole timeline, with smooth zoom from the whole file down to single samples.
  • Timecode ruler, selection with an exact readout, and playback of the edited timeline with a moving playhead.
  • Transport with play, steps between splices, the counter, and level meters for what is playing: a bar for each channel on a dB scale, a peak-hold tick and a clip light.
  • Activity log listing each edit with its author, session and time. The person's edits are amber and agents' are blue-green. Selecting a row jumps to that spot. Any edit can be undone on its own, and an agent's whole session in one step.
  • Splices marked on the timeline in their author's colour. Selecting one shows the audio that was removed there.
  • Labels, the notes agents leave for review, as speech bubbles beside the splice marks, in their author's colour, with a line over the range each one marks. Pointing at a bubble shows the note in a card, and clicking it selects the range.
  • Level edits (gain, fades and mutes) marked along the foot of the waveform in their author's colour.
  • Open and Export through the system's file dialogs. An export runs in the background and shows how far it has got. With no project, the window starts empty with an Open button.
  • Files tab (M3), the third tab in the side panel beside Activity and Labels: a file browser for adding more audio to the open project. It lists folders and the audio files scrubr can read, each with a Play button to hear it first. "Insert" puts a file into the timeline at the playhead, and "Track" lays it on a new track from the playhead. It also lists the files the project already uses.
  • Tracks (M3) as stacked lanes under one ruler, each with its name, level, pan, mute and solo. A selection can be muted on one track alone, and a track can be removed. Cuts always act on every track.
  • Live reload when the project file changes on disk, with a short notice naming the edit. The transport's notice line is empty unless there is something to say.
  • One menu button holds every command, the same on all three platforms. The same list drives the tool buttons and the keyboard shortcuts.
  • No chat or prompt box. Agents drive scrubr from the CLI; the window is for hearing, reviewing and refining what they did.

Shared editing

An agent and a person can edit one project in the same sitting without losing work.

  • Locked, versioned writes. A command takes an OS file lock next to the project, reads the project, checks the version, writes a temporary file and renames it over the project. The lock makes the check and the rename one step, so two writers can't both pass. A killed command releases the lock and leaves the previous version intact. On Windows the rename is retried briefly if another program has the file open.
  • Version checks. An agent that worked out positions at version N passes --if-version N. If you edited in between, the command exits with code 3, and the agent re-reads and recomputes instead of cutting stale positions.
  • Live reload. The GUI watches the project file. When it changes, the GUI reloads, keeps your view and playhead, and shows a short notice naming the new edit.
  • Authorship. Every edit records an author and a session, taken from --author and --session or the SCRUBR_AUTHOR and SCRUBR_SESSION environment variables. Edits made in the GUI are recorded as "you".
  • Session undo. One action reverts everything an agent did in one run, even when your own edits came after it. Edits are stored in source coordinates, so your later edits and labels stay where they were.
  • Notes in both directions. Agents mark spots they are unsure about with labels. Your GUI edits appear in scrubr history, so the agent can see what you changed.

Transcription

Decidedtranscribe runs OpenAI's Whisper models on the person's own machine, in pure Rust, through the whisper-candle-core crate. It is an optional Cargo feature, transcribe, off by default, so the standard build carries no machine-learning code and says so if the command is run.

  • Model install. No model ships with scrubr. scrubr transcribe --fetch-model base.en downloads one from Hugging Face once, about 290 MB for base.en, the default. That is the only step that uses the network. A model can also be given as a folder.
  • Privacy. Audio never leaves the machine.
  • Why Whisper. It gives a start and an end for every word, takes any vocabulary, and the pure-Rust build needs nothing beyond cargo (checked on Windows so far). Two smaller engines were tried first. vosk-rust returned no word times and needed its models converted by hand. utter recognises only a fixed grammar of a few hundred words.
  • How it runs. The timeline is rendered with its edits, mixed to mono, resampled to 16 kHz and handed over in pieces of at most five minutes, each split at the quietest moment near its end. Digital silence is skipped.

Measured with base.en on one Windows desktop, CPU only:

Cutting by phraseWord times are not exact enough to cut on. The agent finds the phrase in the transcript, asks analyze --quietest for the quietest moment between the word inside and the word outside each end, cuts there, and transcribes again across each join to check that the phrase is gone and its neighbours are intact. On the podcast this removed a sentence in mid-conversation and a whole sponsor break cleanly. On the meeting it lands in the right pause for about five ends in six, and the check catches the rest.

A fixed silence threshold does not carry across recordings: at −45 dB the podcast has almost no pauses, and the quiet meeting's soft speech counts as silence. The agent guide says to check loudness first.

Stem separation

DroppedSplitting a stretch of mixed audio into stems, such as a voice and the music under it, was planned as a milestone. A spike tried four engines, and scrubr stems was built once in the core and the CLI. It was then taken out again and is not in scrubr. This section records what was found, so that the work is not repeated blind.

The four engines were built and run on one Windows desktop (16 threads, 32 GB, an RTX 3060). The test material was a real voice and a synthetic one, each mixed over two pieces of music at two levels, with the clean voice and the music kept so the result could be scored. Nobody listened to the results.

EngineVoice, music 12 dB under itVoice, music as loud as itWords a speech model gets wrong5 minutes takesMemory
Nothing: the mix as it is11 to 12 dB−1 to 0 dB11%, 17%
Spleeter, two stems, ONNX Runtime, CPU11 to 13 dB6 dB11%, 19%11 s1.3 GB a minute of audio as run; can be cut down
DeepFilterNet 3, pure Rust, CPU14 dB6 to 7 dB6%, 19%43 s0.4 GB
HTDemucs, ONNX Runtime, CPU16 to 19 dB12 to 13 dB2%, 9%288 s5.1 GB
HTDemucs, Rust on Burn, CPU19 dBAbout 19 minutes for one minute of audio1.0 GB
HTDemucs, Rust on Burn, GPU19 dB13 dB3%, 8%101 s, of which about 50 s is start-up1.1 GB, plus the graphics card's

The voice columns are the signal-to-distortion ratio of the separated voice against the clean one, on the real voice; higher is better, and the first row is what doing nothing scores. The words column is how far a transcript of the separated voice is from a transcript of the clean voice, at the two music levels, over 127 words: a small sample.

  • Only HTDemucs does the job. It lifts a talking voice off music well even when the music is as loud as the voice, and a transcript of its voice is close to one of the clean voice. Spleeter is very fast and leaves the voice no cleaner than the mix. DeepFilterNet helps when the music is quiet and not when it is loud, and gives no music stems: it is a noise reducer.
  • Speed. On a CPU, HTDemucs through ONNX Runtime ran at about the speed of the audio and needed 5 GB. On the graphics card the Rust build split five minutes in about 50 seconds once started, and each start cost another 50. On a CPU alone the Rust build took about 19 minutes for one minute of audio, with other work running beside it: usable for a short stretch and no more.
  • Building. The Rust engines built with cargo alone. ONNX Runtime's ready-made library would not link with the Visual Studio 2019 tools on this machine; it worked once the runtime was loaded from a DLL, which scrubr would then have to ship for each platform.
  • Licences. Spleeter's models are MIT and were trained on Deezer's own recordings. DeepFilterNet's code and models are MIT or Apache-2.0. The HTDemucs code is MIT, but its authors give no licence for the trained model, which was trained on MUSDB, a research-only collection, and 800 more songs. Copies that others have converted carry MIT or Apache-2.0 labels that the authors never gave.

What the built command showed

  • The design held. Each stem was an ordinary track attached to the same audio as the range it came from, added as one edit. What the model's stems did not add up to went into the last stem, so with the original muted over the range the mix was sample for sample what it had been until a stem was changed.
  • It did the job by measurement. On a 30-second stretch of a voice over music the separated voice scored 18 dB against the clean one, where the mix scores 10.5. Turning the rest down 12 dB left the voice 6.6 dB clearer, and undoing the session gave back the original audio exactly.
  • The drawbacks found. The model that works has no licence. Without a graphics card the Rust engine needs about twenty minutes for a minute of audio. With one, every run spends about 50 seconds starting up. The command line program grew from 15 MB to 59 MB.

If it is taken up again

  • ONNX Runtime ran HTDemucs about twenty times faster on a CPU than the Rust engine did, at the cost of a native library for each platform. Fetching that library on demand, as the model was, is the likely way to make it usable without a graphics card.
  • A model with a clear licence that separates speech from music as well as HTDemucs would remove the other objection. Neither Spleeter nor DeepFilterNet does.

Effects

Planned for M5. An effect changes how a stretch of audio sounds: it takes out rumble or hiss, evens out a level, turns music down under a voice. A person or an agent applies one to a selection, to a whole track or to everything. This section is a plan. None of it is built.

Why these fitThey are ordinary signal processing. They need no model, no graphics card and no download, and they run many times faster than the audio plays on any machine. That is the opposite of what stem separation asked for.

How an effect fits scrubr

  • An effect is an edit. It has an author and a session, it is in the log, and it is undone, redone and reverted like a cut. The log stores which effect, its settings as plain numbers, the audio it was applied to in source coordinates, and the track if one was named.
  • The sources are still never changed. The effect runs once and writes the processed audio to a file in the project's cache folder. Playback, analysis and export read that file wherever those frames of that track are heard. Every effect gives the same output for the same input, so if the file is lost it is made again from the log.
  • No processing while playing. Because the result is a file, playback costs what it costs today and a frame's value still depends only on its position. It also means there is no live preview: apply, listen, undo or adjust.
  • Range and track. With no range an effect covers the whole timeline. --track T applies it to that track alone; without it, to every track, each processed by itself.
  • As recorded, or after level edits. By default an effect hears the track's audio as recorded, and the gains and fades on it apply on top of the result, as they do for every other edit. With --after-levels it hears the audio after the level edits already made. Those edits are then part of the result and are not applied a second time; level edits made later still apply on top. A compressor or a limiter is the usual reason to ask for this.
  • Effects stack. A later effect on the same audio hears the earlier one's result. If an earlier effect is undone or reverted, the later ones are run again on what is now there. The same holds for an effect that heard level edits which are later taken back. The log is the record; the files follow it.
  • Disk. The cache keeps the files playback needs, which for a chain of effects is the last one. The steps in between are dropped and made again from the log if an undo needs them.
  • Edges. The effect hears a little audio before the range so that a filter has settled by the first frame, and its result is crossfaded 5 ms against the original at each end.
  • Effects that change length are a different kind. A change of tempo or speed makes time longer or shorter, and time is shared by every track. They act on every track or are refused. They are in the second wave.
  • Measuring is not an effect. Finding clipping or reading a spectrum changes nothing, so those are analyze flags, and their findings can be left as labels for the person.
  • Written from scratch. Each effect is built from published signal processing. No code is taken from Audacity or any other GPL program.
$ scrubr analyze ep42.scrubr --spectrum --silence -50dB:1s
$ scrubr fx ep42.scrubr highpass --hz 80
$ scrubr fx ep42.scrubr denoise --profile 12:03.2..12:04.6 --reduce 12dB
$ scrubr fx ep42.scrubr compress --threshold -24dB --ratio 3
$ scrubr fx ep42.scrubr duck --track music --under voice --by 10dB
$ scrubr fx ep42.scrubr limit --ceiling -1dB --lufs -16 --after-levels

The command and its flags are a sketch. In a batch an effect is one more operation, { "op": "fx", "effect": "highpass", "hz": 80 }, under the same batch rule.

Three of the first wave do more than save steps. The limiter answers an open question about normalize. Auto duck gives most of what stem separation was wanted for whenever the music is on a track of its own. Noise reduction is something an agent can drive by measurement: analyze --silence finds a stretch with no speech, and that stretch is the noise to learn.

In the window

  • An Effects menu that acts on the selection, or on the whole timeline when there is none, and on the picked track or on all of them.
  • Each effect opens a small card with its settings and an Apply button. The card remembers the last settings used.
  • An applied effect is a row in the activity log, and a mark along the foot of the lanes in its author's colour, as level edits are.

Not settled

  • Trying a setting. Tuning a compressor by ear takes several tries. Apply and undo may be enough, or the card may need a way to hear a few seconds before applying.
  • Running again. Stacking means an undo early in a chain can set several effects running again over a long recording. How long that takes, and what the window shows meanwhile, has to be measured.

Milestones

  1. M0

    Rune spike

    A few days. Load a 1-hour WAV, build a min/max peak pyramid, draw it in a Rune window, zoom and scroll it, and play it through cpal with a moving playhead.

    Exit testSmooth zoom on a 1-hour file with no audio dropouts. If Rune can't draw custom geometry well enough, move the GUI plan to egui and keep everything else.

  2. M1

    Core and CLI

    Project file, edit log in source coordinates, locked and versioned atomic writes with --if-version, decoding, the edit commands with default crossfades at joins, author and session on every edit, undo and history, analysis (loudness, peaks, silence, envelope), optional transcription with word timestamps, PNG rendering, WAV and FLAC export, help --agent and AGENTS.md.

    Exit testAn agent with only the binary and the guide cleans up a 1-hour podcast: removes long silences, finds a named segment in the transcript and cuts it, hits −16 LUFS with true peak at or under −1 dBTP, fades both ends and exports FLAC. The result passes a listening check.

  3. M2

    GUI

    Open a project, stereo waveform, timecode ruler, selection, playback, history panel showing author and session, live reload when the project file changes, undo and redo, keyboard shortcuts and export.

    Exit testYou can audit and fix the M1 agent's work without touching the CLI.

  4. M3

    Shared editing, files and multitrack

    Session undo, labels on the timeline, notices naming each outside edit, and GUI write retries after a version conflict. Authorship arrives in M1 and live reload in M2.

    The Files tab in the side panel, for hearing and adding more files to the open project.

    Multitrack: several tracks in one project, scrubr track and --track in the CLI, stacked lanes with level, pan, mute and solo in the window, and a mix-down for playback and export. All of it is built. In the window each track's level moves in 1 dB steps and its pan in tenths, and each step is an edit in the log. A press in a lane picks its track, Shift+M then mutes the selection on that track alone, and every track but the main one can be removed from its lane. A file added from the Files tab is read on its own thread, so a long or compressed one does not stall the window.

    Exit testAn agent and a person edit the same project in one sitting and no edits are lost. A two-microphone recording and a music bed are brought together from the Files tab, cleaned up by an agent track by track, and exported as one mix.

  5. M4

    Extras

    MP3 export, spectrograms, and cut-by-words commands on top of the transcript.

  6. M5

    Effects

    Effects on a selection, a track or everything, each one an edit: the way an effect is stored and played, scrubr fx and the two new analyze flags in the CLI, the Effects menu in the window, and the first wave: EQ, compressor, limiter, noise gate, noise reduction, click removal and clip repair, auto duck, invert and reverse.

    The second wave, reverb, echo, tempo and pitch, follows a spike on time-stretching and is not part of this milestone.

    Exit testAn agent takes a noisy, uneven recording with music on a second track. Working from measurements alone it removes the rumble and the hiss, evens the voice, ducks the music under it and reaches −16 LUFS without passing the ceiling. A person hears the result, changes one setting, and undoes the whole session in one step.

Risks

RiskMitigation
Rune is pre-release and its API may changePin a revision, keep the GUI crate thin, keep the core free of Rune.
Rune's support for custom drawing is unconfirmedM0 tests it first. egui is the fallback.
Rune lists native audio as missingPlayback runs on a cpal thread. The GUI reads an atomic playhead position each frame.
Long files are slow to draw and scrubPeak pyramid cache, streaming decode, seek tables for compressed formats.
Agent and person write at the same momentA file lock around each write, and --if-version with exit code 3 for stale positions. The GUI retries after reloading.
Normalize can't reach its target without clippingGain stops at the true-peak ceiling and the reply reports the loudness achieved. The limiter planned for M5 is the way past that.
Effects written from scratch are wrong, or sound poorEach has a test that measures it: a filter's response with a sweep, a limiter that never passes its ceiling, noise reduction scored on speech with known noise added. A person listens before M5 is called done.
With no live preview, effects are slow to tune by earApplying and undoing are quick, and the card keeps the last settings. Whether to add a way to hear a few seconds first is an open question.
Processed copies of long recordings fill the diskThey live in the cache and can be made again from the log. Only the last file of a chain is kept.
Undoing an early edit sets a chain of effects running againEffects run many times faster than the audio plays. The time is measured on an hour-long recording before M5 is called done, and the window shows progress as it does for an export.
Agents misjudge audio from numbers aloneLabels for human review, PNG renders, and transcripts from M1.
Hard cuts click, and an agent can't hear itJoins crossfade by default.
Transcription brings a heavy dependency and a large modelOptional feature. The binary builds and works without it, and no model is bundled. The engine is pure Rust, and the model is one download of about 290 MB.
Transcripts have wrong words and loose word times, worst where people talk over each otherCuts go at the quietest moment between words, not at word times. The agent transcribes again across each join, and labels what it is unsure of.
The Whisper crate is young (0.1) and tested here on Windows onlyIt sits behind one trait in the core, so another engine can replace it without touching the CLI.
Multitrack arrives after the core, the CLI and the window were built around one timelineOne track is the plain case of the same model, so earlier projects and commands keep working. The file format number goes up. Source coordinates, the batch rule and version checks do not change.
License contaminationNo Audacity code. LAME only as an optional, dynamically linked feature.

Open questions

  • Should scrubr undo from the CLI undo only the caller's own edits?
  • After an undo, does a new edit discard the undone edits, or keep them recoverable as a branch?
  • One project file plus a cache folder, or a single project folder?
  • Once the limiter is there (M5), should normalize use it by itself to reach its target on peaky speech, or only when asked?
  • Is apply-then-undo enough for tuning an effect by ear, or does the window need a way to hear a few seconds before applying?
  • When a cut covers audio that an earlier edit had already removed, should it claim that hidden audio too, so it stays hidden if the earlier edit is reverted?
  • Is base.en the right default model, or should recordings with several speakers default to a larger one such as small.en, about 1 GB?
  • Should release builds include the transcription feature, or stay without it and leave it to people who build from source?
  • Should recording from a microphone ever be in scope?
  • Is a browser build through Rune's WebGPU target worth revisiting once it matures?
